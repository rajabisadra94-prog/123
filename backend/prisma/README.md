# مهاجرت‌های دیتابیس — قواعد کار

## ⛔ دیگر از `prisma db push` استفاده نکنید

`db push` شِما را مستقیم روی دیتابیس می‌نویسد و **هیچ فایل مهاجرتی نمی‌سازد**.
نتیجه‌اش این می‌شود که دیتابیسِ شما جلو می‌رود ولی پوشهٔ `migrations/` عقب می‌ماند،
بدون اینکه هیچ خطایی ببینید — حتی `prisma migrate status` می‌گوید «up to date»،
چون فقط جدولِ `_prisma_migrations` را نگاه می‌کند نه ساختار واقعی را.

دقیقاً همین اتفاق افتاد: بین ۰۷ خرداد و ۲۹ تیر ۱۴۰۵، ‏**۱۷ جدول** (از جمله
`Message`، `JournalEntry`، `JournalLine`، `Supplier`، `ForwardingCargo`) فقط در
دیتابیسِ توسعه ساخته شدند. اگر با همان وضع روی سرور مستقر می‌شد،
`migrate deploy` دیتابیسی ناقص می‌ساخت و سامانه بالا نمی‌آمد.
مهاجرت `20260720120000_catch_up_to_current_schema` این شکاف را جبران کرد.

## روش درست

### تغییر شِما در توسعه

```bash
# ۱) schema.prisma را ویرایش کنید
# ۲) مهاجرت بسازید (هم فایل می‌سازد هم روی دیتابیس اعمال می‌کند)
npm run db:new -- add_supplier_wechat
```

نام مهاجرت را کوتاه و توصیفی بگذارید: `add_supplier_wechat`، نه `update1`.

### قبل از هر کامیت

```bash
npm run db:status    # مهاجرت اعمال‌نشده‌ای مانده؟
```

### روی سرور (تولید)

```bash
npm run db:deploy    # فقط اعمال می‌کند؛ هرگز چیزی نمی‌سازد و چیزی پاک نمی‌کند
```

`migrate dev` را **هرگز** روی سرور اجرا نکنید — ممکن است دیتابیس را ریست کند.

## بازگشت به نسخهٔ قبلی

برگرداندن **کد** آسان است، برگرداندن **شِما** نه. Prisma «down migration» ندارد.
پس قاعدهٔ طلایی هنگام تغییرات ساختاری:

> **اول اضافه کن، بعداً حذف کن** (expand / contract)

مثلاً برای تغییر نام یک ستون، در یک انتشار ستون جدید را اضافه و پر کنید و کد را
طوری بنویسید که هر دو را بخواند؛ ستون قدیمی را چند انتشار بعد — وقتی مطمئن شدید
برنمی‌گردید — حذف کنید. این‌طور اگر مجبور به بازگشت شدید، دادهٔ کسی نمی‌سوزد.

**و همیشه قبل از هر استقرار، بکاپ دیتابیس بگیرید.**

## بازسازی از صفر (برای تست)

```bash
createdb factory_test
DATABASE_URL="postgresql://…/factory_test" npx prisma migrate deploy
DATABASE_URL="postgresql://…/factory_test" npm run db:seed
```
